Bytecode An interactive monograph on the CPython interpreter

Bytecode

The compact instructions a Python program is compiled to, the machine that executes them, the strategies that keep it efficient, and the memory model that keeps it correct.

An interactive monograph in ten sections, with six live figures. Reading time roughly fifty minutes. The figures are operable by mouse, touch and keyboard, and the document conforms to WCAG 2.2 AA. Built as a single static page in vanilla HTML, CSS and JavaScript, with no framework and no build step.

Abstract

The Python language is a specification; CPython is the canonical implementation that turns that specification into actual computation on real hardware. CPython does the work in three movements. It parses the source into an abstract syntax tree and compiles that tree into a sequence of bytecodes, the compact instructions of a stack machine. It executes those bytecodes by an evaluation loop that pushes and pops values on a per-frame stack, calls into C implementations of each opcode, and unwinds frames on return. And it manages memory by reference counting, supplemented by a cyclic garbage collector that reclaims unreachable cycles the refcount alone cannot. The architecture has been remarkably stable since the early 1990s, while the engines built around it have changed considerably: the specialising adaptive interpreter introduced in CPython 3.11 made the bytecode loop dramatically faster at no source-language cost, and the free-threaded build introduced as an option in CPython 3.13 has begun to remove the global interpreter lock that long limited the parallelism of pure-Python code.

This document develops the interpreter from the foundation. It treats the source-to-bytecode compilation, the value stack, the call stack, reference counting, cyclic garbage collection, the specialising adaptive interpreter and the threading model. Every figure runs the genuine mechanism on synthetic input: the disassembly figure walks the program counter through a real opcode sequence; the value-stack figure applies each opcode to a real stack; the reference-counting figure increments and decrements integer refcounts on a real object graph; the cyclic garbage-collection figure executes a working mark-and-sweep; and the specialising-interpreter figure increments execution counters and rewrites the opcode at the documented threshold.

1Reading the language one instruction at a time

A line of Python code such as c = a + b looks atomic to the reader and is anything but to the machine. By the time it executes, the source has been parsed into a tree, the tree has been compiled into a sequence of bytecodes, and those bytecodes have been run by an interpreter that loads each operand onto a stack, performs the addition, and stores the result back into a local. Each of those steps is a separate piece of machinery, and CPython exposes most of them. The dis module disassembles a function into the bytecodes it compiles to; the sys.settrace hook observes the interpreter as it runs; sys.getrefcount reads the reference count of any object; gc controls the cyclic garbage collector. The interpreter is, by the standards of language runtimes, unusually inspectable.

The reason to know the interpreter at this level is not, in most working software, performance. Pure Python code is at most a few times faster on CPython 3.13 than on CPython 3.10, and a hot numerical loop in Python remains an order of magnitude slower than the equivalent in C. The reasons are diagnostic and structural. Tracebacks become legible when one knows what a stack frame is. Memory leaks become reproducible when one understands which kinds of cycle the cyclic collector can and cannot reclaim. The performance regressions between Python versions become explainable when one understands which opcodes specialise and which do not. And the surprising behaviour of certain idioms, such as the difference between mutating a default argument and replacing it, turns out to follow from concrete mechanical facts about the interpreter rather than from any subtlety of the language specification.

This document treats the interpreter as a working machine to be observed. The figures execute synthetic programs and expose, at each step, the program counter, the value stack, the call stack, the reference counts, the reachability graph and the specialisation counters. Each figure corresponds to one of the parts of CPython's runtime, and the prose that surrounds them gives the names by which to find the same parts in the source tree of the interpreter at github.com/python/cpython.

2The source, the compiler and the bytecode

When CPython is given a Python source file it does not interpret the text. The text is first lexed into tokens by the C tokenizer in Parser/tokenizer.c, then parsed by the PEG parser described in PEP 617 into an abstract syntax tree, and then lowered by the compiler in Python/compile.c into a code object. The code object is the runtime artefact: it contains the bytecode as a sequence of bytes, the constants the function uses, the names of its local variables, and the metadata that maps each bytecode back to a source line for tracebacks.

The bytecode itself is a sequence of opcodes, each consisting of a single-byte instruction and a single-byte argument. In CPython 3.6 the format was widened from variable-length to a uniform two-byte instruction, an arrangement called wordcode that simplifies the dispatcher and reduces the number of memory loads per instruction. The instruction set is small: in the order of a hundred and fifty opcodes, of which the dozen most common, the loads, stores, the binary operators, the comparison, and the function call, dominate almost every program.

The figure above shows a tiny Python function alongside its disassembly. The program counter advances by the arrow keys when the figure is focused, and the active source line and active bytecode are marked with a leading chevron, an aria-current attribute and a highlighted background, so that the connection between the two views is visible at every step. The opcodes shown, LOAD_FAST, BINARY_ADD, STORE_FAST, LOAD_CONST, BINARY_MUL and RETURN_VALUE, are the real CPython opcode names; the arguments are the names of the function's locals or the indices of its constants. Running the same example in Python with dis.dis(total) produces the same listing.

Some opcodes carry a richer payload than their byte width suggests. The opcode EXTENDED_ARG prefixes the next instruction with the high bits of its argument, allowing arguments larger than two hundred and fifty-five. The CALL opcode carries a small argument and reads its full call signature, including keyword arguments, from a small inline cache attached to the bytecode. The CPython compiler also performs limited optimisations before emitting code: constant folding, dead-code elimination, and peephole substitutions that combine common opcode pairs. The compiler is intentionally simple, leaving heavier optimisation to the runtime, which the seventh section describes.

The code object itself is, in CPython 3.11 and later, a richer structure than it used to be. Alongside the bytecode it carries inline caches that the specialising interpreter writes into at runtime, a positions table that maps each bytecode to the column range of the source it came from (so that error messages can point at the failing sub-expression rather than the whole line), the exception table that the eval loop consults to find handlers when an exception propagates, and a localsplus table that consolidates the function's parameters, local variables, cell variables and free variables in a single addressable array. Each of these tables is the result of a separate piece of engineering work that addressed a definite limitation of the previous code-object layout, and together they make the code object the central artefact through which the eval loop interacts with the rest of the runtime.

3A history of CPython internals: a literature review

CPython has had three principal eras of internal work, and the present interpreter is the layered result of all three. The account that follows is causal: in each case the question is which limitation of the previous era the next set of changes was made to address.

The first era covers the original implementation. Guido van Rossum described Python in a 1995 technical report and a small early paper, and the implementation he wrote was a textbook tree-walking interpreter that lowered the abstract syntax tree to a stack-based bytecode and ran the bytecode in a simple eval loop. The architectural decisions of that era persist into the current interpreter: the stack machine, the reference-counting memory manager, the per-thread Python state and the global interpreter lock that simplifies it, the convention that the C API exposes the internals to extension modules. These choices were taken because they made the runtime small, portable and easy to embed, and they had the corollary that the runtime did not aspire to compete on raw speed with the just-in-time compilers that were already beginning to appear in academic Lisp and Smalltalk implementations. Aycock's 2003 survey [1] places the state of just-in-time compilation at that point: it had become well established in the academic community but had not yet entered any mainstream dynamic-language production runtime.

The second era is the line of work that took place outside the CPython codebase and demonstrated that Python could be much faster. PyPy, started in the early 2000s and described by Bolz and colleagues in 2009 [2], built an alternative Python implementation in a restricted subset of Python called RPython, and applied to that subset a meta-tracing just-in-time compiler that generated efficient machine code for hot loops. PyPy was, and remains, much faster than CPython on pure-Python workloads, by factors of five to twenty on common benchmarks, but it did not displace CPython in deployment because of the gravitational mass of the existing C extension ecosystem: NumPy, lxml, cryptography and thousands of smaller packages all depend on the CPython C API, and PyPy's alternative API, cpyext, although valiant, never closed the compatibility gap. Pyston, started at Dropbox in 2014 [3], attempted a different tactic, building a JIT on top of the LLVM toolchain that ran in place of CPython's eval loop while preserving the C API; it was partially successful at speeding up production workloads and was eventually retired. The Truffle project at Oracle Labs [4] went a third route, with a partial-evaluation framework on top of which GraalPython runs; again the technique works and again the C API compatibility question kept it from CPython displacement.

The fact behind the second era's history is that every Python implementation faster than CPython either gave up some of the C API compatibility or lived as an alternative interpreter that users could not assume their dependencies supported. The lesson that the third era of work has taken is that the same speed gains must be obtained inside CPython itself, with the C API preserved. The line was begun, intellectually, by Mark Shannon's PhD work on type inference and deoptimisation [5], which laid out how a dynamic-language interpreter could specialise its operations to observed types without losing the ability to fall back when the types changed. It became practical with PEP 659 [6], the specialising adaptive interpreter, which Shannon led into CPython 3.11. The companion piece, PEP 657 [7], added fine-grained error locations so that the new interpreter could point users to the exact failing sub-expression rather than only the failing line. The Faster CPython project, sponsored by Microsoft, has continued to deliver substantial speed-ups in each release since.

The third era's other major thread is the slow removal of the global interpreter lock. PEP 703 by Sam Gross [8], accepted in 2023 and shipped as an option in CPython 3.13, makes the GIL removable at build time, with the reference-counting memory manager rewritten to use atomic operations and the cyclic garbage collector adjusted to coordinate with a multi-threaded mutator. The trade-off is that the free-threaded build is currently slower on single-threaded workloads than the build with the GIL retained, because the atomic refcount operations cost more than the unguarded increments of the original. The expectation is that the gap will narrow as the implementation matures, and that free-threaded CPython will become the default once it does. The Instagram fork called Cinder, the Pyjion JIT, and the academic Skybison interpreter at Meta have all contributed engineering ideas to this thread.

Two threads run through this history. The first is the steady professionalisation of CPython's performance work: from a tree-walking interpreter written quickly in C, through a long period in which raw performance was treated as someone else's problem, into a sustained engineering effort to make CPython itself fast without compromising compatibility. The second is the gradual replacement of architectural commitments that were taken for granted: the inflexibility of the bytecode dispatcher is being replaced by specialisation; the global interpreter lock is being made optional; the memory manager is being audited against the assumption of multi-threaded mutation. The CPython of 2030 will look, internally, substantially different from the CPython of 2010, and it will run almost the same Python programmes from the same surface language.

4The value stack

CPython is a stack machine. Each frame, the runtime object corresponding to one invocation of a function, owns a small value stack on which the interpreter places the operands and results of bytecodes. Loading a local pushes its current value; storing a local pops the top of the stack into the named binding; a binary operator pops two values, computes a result and pushes the result back. The opcodes are short and the dispatcher is simple, and the stack-machine choice was made for exactly that simplicity.

A stack-based bytecode is one of two common designs; the other is a register-based bytecode in which each opcode names its operands and result by small integers. Lua and the V8 JavaScript engine's Ignition interpreter both use register machines. The trade-off is well understood: register code is usually shorter, by an opcode count, because operations that a stack machine would express by loading and storing twice can be expressed by a single three-register operation; but stack code is more uniform, simpler to generate, and easier to optimise peephole-style. Python's choice has not changed across its history, although the specialising interpreter of the seventh section has begun to add register-like behaviour for the most common opcode sequences.

The figure above runs the bytecode of the previous section against a real value stack, presented as a DOM table for screen readers and zoom users. Stepping through the bytecode pushes and pops values, and the cell at depth zero is the top of the stack at any moment. The STORE_FAST instruction pops without pushing; LOAD_CONST pushes a literal constant; BINARY_ADD and BINARY_MUL pop two values and push one; the final RETURN_VALUE takes the top of the stack as the function's return.

Two practical notes attach to the value stack. The maximum stack depth for a function is computed by the compiler and stored as the co_stacksize attribute of the code object; the interpreter pre-allocates that many slots for the frame at call time, so stack overflow inside a single function is impossible by construction. Deep recursion is limited by a separate mechanism, the call-stack depth that the ninth section covers. The other note is that the stack is not visible from Python except via the sys.settrace hook, which observes execution at the granularity of frames and source lines; the stack contents at intermediate points within a line can be reached only with C-level debugging or with the dis module's analysis of what the bytecode does.

The eval loop itself sits in Python/ceval.c and is one of the most-edited files in CPython's history. It consists of a giant switch on the opcode of the current instruction, with a case for each opcode that pops its inputs from the stack, calls the C implementation of that operation, pushes the result and advances the program counter. On a compiler that supports computed gotos the switch is implemented with a dispatch table indexed by opcode, which removes a branch misprediction at the top of every iteration and was one of the largest single performance improvements in the loop's history. The loop also services exceptions: when a C-level operation signals failure, the loop walks the exception table attached to the code object to find the handler, unwinds the stack to the handler's expected depth, and resumes dispatching from the handler's bytecode offset.

5Reference counting

CPython manages memory primarily by reference counting. Every Python object carries an integer field, the reference count, which tracks how many references currently point at it. When a name is bound to an object the count is incremented; when a binding goes out of scope or is rebound to a different object the count is decremented. When the count reaches zero the object is immediately reclaimed: its finalisers run and its memory is returned to the allocator. The immediacy is a deliberate property of the design, and is why CPython's memory footprint is often smaller than that of garbage-collected languages: objects do not wait for a collector cycle before their resources are released.

The figure below executes a short script of name bindings on a small object graph and shows each object's reference count updating as bindings are added and removed. The script creates a list, binds three names to it, deletes one of those bindings, creates a second list, rebinds one of the surviving names to the second list, and deletes the remaining two names of the first list; the figure follows the counts through to the point where the first list's count reaches zero and the object is reclaimed.

Reference counting has two well-known limitations. The first is its cost: every binding and every rebinding incurs an atomic increment or decrement, which dominates the cost of trivial operations on small objects and contributes the largest share of the overhead of free-threaded CPython, where the increments and decrements must be properly atomic with respect to other threads. The second is that it cannot reclaim reference cycles: two objects that reference one another keep each other's counts above zero indefinitely, even when no other part of the program can reach them. The sixth section addresses this with the cyclic garbage collector.

The C API exposes the reference count through the Py_INCREF, Py_DECREF and Py_XDECREF macros, and a substantial part of the discipline of writing a CPython extension is the discipline of balancing those macros so that no reference is leaked or double-freed. The cython, pybind11 and nanobind tools each remove that burden in their own way, and the move toward higher-level binding generators has been driven, in part, by the difficulty of getting reference-count management right by hand in non-trivial extensions.

The integer in the reference count is Py_ssize_t, a signed integer wide enough to address every byte of memory the platform supports, so the count cannot overflow on any plausible workload. The header that contains the count also contains the type pointer of the object, which is the single piece of metadata every CPython object carries and which the eval loop dispatches against. The total per-object overhead is therefore two pointers' worth of memory, twenty-four bytes per object on a sixty-four-bit system once the count is included, which is the per-object floor that any Python program pays. Variable-sized objects, including tuples, lists and strings, carry their length in a second header field, the ob_size, used by the allocator to determine how much memory the object occupies. The C structure that combines these fields, PyObject, is the most-included header in the CPython codebase and the one whose layout decisions have the most pervasive effects on the rest of the runtime.

6Cyclic garbage collection

A reference-counting system cannot reclaim a cycle: two objects that reference one another keep each other alive even after every external reference has been removed. CPython solves this with a generational cyclic garbage collector that runs periodically and reclaims the cycles that the reference count alone cannot. The collector is in Modules/gcmodule.c and is exposed to Python through the gc module.

The collector observes that, for an object to be unreachable, no chain of references from any root must reach it. The roots in CPython are the per-thread frame stacks, the per-interpreter modules and built-in references, and a handful of other live containers. A standard mark-and-sweep over the heap would identify the unreachable set: starting from the roots, every object reachable by following references is marked; on a second pass everything unmarked is reclaimed. CPython does something subtler in practice. To avoid the cost of marking every object on every collection it uses generations: objects are placed in a young generation when they are created, and objects that survive a generation's collection are promoted to an older generation, where they are scanned less often. The generational hypothesis, that most objects die young, is empirically true in Python programs, and the saving is substantial.

The figure above runs a simplified mark-and-sweep on a small object graph. The graph contains a reachable object accessible from the root, a cycle of two mutually referencing objects unreachable from any root, and a third object that the root reaches by a different path. Pressing Run GC performs the mark phase, traversing references from the root and marking every reached object, then the sweep phase, which reclaims everything unmarked. The cyclic pair vanishes; the reachable objects survive. The active object selected by the radiogroup shows its current reachability status in the stats below the figure.

Two design notes complete the picture. The collector treats only objects that the interpreter believes might participate in cycles; many built-in types, such as integers, strings and tuples of immutable elements, cannot form cycles and are excluded from the collector's traversal. The collector also handles the awkward case of objects with finalisers (__del__ methods) in a cycle: a cycle of such objects requires the collector to choose an order in which to finalise them, and historically this was a source of bugs and surprising behaviour. PEP 442, implemented in CPython 3.4, revised the protocol so that any object can safely be finalised inside a cycle, removing the long-standing documentation footnote that warned users against the practice.

The collector's interaction with the C extension ecosystem deserves a brief note. An extension that holds references to Python objects from C structures must, if those structures can participate in cycles, expose a traverse function so the collector can walk through them. The convention is the tp_traverse slot on the type object, which the collector calls during the mark phase, passing each contained reference to a visitor function. An extension that participates in cycles but does not implement tp_traverse leaks those cycles; an extension that implements it correctly allows the collector to reclaim them. The same machinery underlies the gc.get_referents function exposed to Python, which returns the references an object holds and is one of the more useful primitives for tracking down memory leaks in long-running services.

7The specialising adaptive interpreter

For most of its history CPython's evaluation loop dispatched a generic implementation for each opcode. The BINARY_ADD opcode would, on each execution, call into the C function that knows how to add two arbitrary Python objects, which then dispatched on their types to the integer, string, list or user-defined-class addition. The cost of that per-execution dispatch dominated the cost of the actual work for most opcodes, and the speed of a Python loop was determined less by the addition than by the bookkeeping around it.

The specialising adaptive interpreter, introduced in PEP 659 [6] and shipped in CPython 3.11, addressed this. Each opcode begins life as its generic form. A small counter inline with the bytecode tracks how often the opcode has executed. After a threshold the interpreter looks at the actual types it has been operating on and rewrites the opcode in place to a specialised form: a BINARY_OP that has been seeing two integers becomes BINARY_OP_ADD_INT, which skips the type-dispatch and the boxing-unboxing for the common case. If the assumptions of the specialised form are violated, for example because the operands are now strings rather than integers, the opcode deoptimises to its generic form and may re-specialise later if the types stabilise again.

The figure above runs a small loop and shows the counter incrementing on each iteration; when the counter reaches the threshold the opcode is recorded as specialised, and subsequent iterations execute the specialised form. The per-iteration cost is shown shorter for the specialised iterations, with a non-colour glyph marking those bars so the distinction survives in a monochrome rendering. The threshold and the precise mechanism by which the interpreter chooses a specialisation are tuning parameters of the runtime; the implementation in CPython 3.13 is more sophisticated than the stylised version the figure presents, but the principle is the same.

The specialising interpreter is the largest change to the CPython evaluation loop since the introduction of the wordcode format. Its consequence is a multi-release stream of speedups across the language, with the largest gains in tight loops on integer and floating-point data, the smallest in code dominated by I/O or by extension calls. The accompanying PEP 657 [7], which added fine-grained error locations, was made necessary by the new interpreter's reorganisation of the bytecode: tracebacks could now report which sub-expression of a line failed rather than merely the line number, a substantial improvement in diagnostic value.

A reasonable question to ask of the specialising interpreter is how it compares with a just-in-time compiler. A JIT compiles hot code paths to machine code that bypasses the eval loop altogether; the specialising interpreter only replaces opcodes in the existing eval loop with cheaper opcodes, leaving the dispatcher in place. The simpler approach has two engineering advantages that have kept CPython on the interpreter side of the design space. It preserves the C API unchanged, which the JIT-based alternatives discussed in the third section have all struggled with. And it does not require a code-generation backend in CPython itself, which keeps the build dependencies and the security surface small. The intermediate step, a copy-and-patch tier that emits small templates of machine code per opcode, is being explored as the next stage in the Faster CPython roadmap.

8Frames and the call stack

A frame is the runtime object corresponding to one invocation of a Python function. It owns the function's local variables, its value stack, a pointer back to its caller, and a record of where execution is suspended. CPython holds the active frames on a per-thread call stack: each call pushes a new frame, each return pops the top frame and restores the caller. The frame object is exposed to Python through sys._getframe and is the underlying representation that inspect uses to walk the stack and that the traceback module formats for printing.

The figure below steps through a short trace of calls and returns. The call stack grows as each call pushes its frame and shrinks as each return pops the top. The active frame, the top of the stack, is the one whose bytecode is currently executing; the frames beneath it are paused at the CALL instruction that invoked the function above them and will resume after that CALL returns.

Two structural changes have affected CPython's frame design in the recent past. The first is the lazy frame creation introduced in CPython 3.11: a function call no longer unconditionally allocates a heap-resident frame object; instead, the per-frame data sits inline in the eval loop's local memory, and a heap frame is materialised only when the program does something that requires it, such as walk the stack with sys._getframe or raise an exception whose traceback wants to reference the frame. The lazy allocation saved both an allocation and the corresponding freeing for the common case of a function that returns normally, and was one of the larger speedups of the 3.11 release.

The second is the introduction of a per-interpreter execution state in PEP 684, alongside subinterpreters, which let a single process host several independent Python interpreters, each with its own modules, threads and call stack. The motivation was a path forward for parallelism on the GIL- enabled build: while a single interpreter is bottlenecked on the GIL, multiple subinterpreters in one process each carry their own GIL and can run in parallel. The subinterpreters feature was made usable from pure Python in CPython 3.13 by PEP 734, and it sits alongside the free-threaded build as a second route to parallel pure-Python code.

9Free-threaded CPython and the GIL

The global interpreter lock has been a fact of CPython since its earliest releases. It is a single mutex that serialises access to interpreter state: a thread that wants to execute Python bytecode must hold it, and the interpreter releases it periodically to allow other threads to run. The GIL exists because the reference-counting memory manager is not thread-safe by construction: a non-atomic increment of a reference count on one thread can race with a decrement on another, with the result that an object is either freed prematurely or leaked. The simplest correctness fix is a coarse-grained lock on the entire interpreter, and that is what the GIL has always been.

The performance consequence is that CPython programs cannot execute Python bytecode on more than one core simultaneously. Programs that are dominated by extension calls or by I/O benefit from threads, because both release the GIL while they wait; programs that are dominated by pure-Python computation do not. The standard workaround has been to run multiple processes via the multiprocessing module, paying the cost of process creation and inter-process communication to get the parallelism back. PEP 684's subinterpreters offered an in-process alternative that avoids the IPC cost, at the price of requiring the program to be structured around the subinterpreter boundary.

PEP 703 [8], accepted in 2023, removes the GIL as a fundamental architectural commitment. It rewrites the reference-counting memory manager to use atomic operations, partitions the cyclic garbage collector's data structures so that they can be updated by multiple threads without contention, and replaces the historical assumption of single-threaded interpreter state with explicit per-thread state where appropriate. The free-threaded build of CPython 3.13 is available as a compile-time option, and the design is for the GIL-free build to become the default once its single-threaded performance parity is established. The trade-off in the current free- threaded build is a small single-threaded penalty, on the order of ten to fifteen per cent, in exchange for genuine parallel execution of Python bytecode across cores. The long-running engineering work on closing that single-threaded gap will be the major story of CPython's performance development over the next several releases.

A practical word on the threading APIs that sit above the GIL is in order. The threading module gives a high-level threading interface; the concurrent.futures module gives a thread-pool abstraction whose ThreadPoolExecutor is the recommended way to parallelise blocking I/O. The asyncio module runs a cooperative event loop on a single thread and uses coroutines to interleave I/O-bound tasks without the overhead of threads; it is the right tool for high-fanout I/O workloads, and the wrong tool for CPU-bound work, which it serialises on its event-loop thread. With free-threaded CPython the calculus shifts: CPU-bound pure-Python work can now scale across cores without the multiprocessing escape hatch, and the standard threading and futures APIs apply unchanged. The asyncio model remains the right one for I/O-bound work regardless of whether the GIL is present.

10Conclusion

The CPython interpreter is built from a small set of named parts, and the document has visited each of them. The compiler lowers Python source into a sequence of bytecodes. The eval loop dispatches each bytecode in turn, manipulating a per-frame value stack. The frame object encapsulates one invocation of a function, and frames sit on a per-thread call stack. Memory is managed primarily by reference counting, with a generational cyclic garbage collector reclaiming the cycles that the refcount alone cannot. The specialising adaptive interpreter rewrites hot opcodes into faster type- specialised forms. The threading model has been governed by the global interpreter lock for most of CPython's history and is now being incrementally freed of it. The combination has made CPython the canonical Python implementation for thirty years, and is the basis on which the language's continued performance evolution is built.

The literature review placed the parts in time and argued that the present interpreter is the layered result of three eras of work: the foundational era in which the architecture was settled; the long middle era in which alternative implementations demonstrated that Python could be faster without proving it could be faster within CPython; and the current era of sustained engineering inside CPython that has delivered substantial speedups in each release since 3.11 and has begun the removal of the GIL. The two threads of that history, the professionalisation of CPython's performance work and the gradual loosening of architectural commitments taken in the 1990s, are visible in every recent release note.

A reader who has followed the development is positioned to read the CPython source itself, which is available on GitHub at python/cpython and is, by the standards of language interpreters, unusually readable. The eval loop is in Python/ceval.c; the compiler is in Python/compile.c; the cyclic garbage collector is in Modules/gcmodule.c; the specialising interpreter machinery is in Python/specialize.c; the threading code is in Python/pystate.c. The PEPs cited in the references are the long-form design documents that describe each change in detail. The combination of source code and PEPs is the reference material this monograph is a guide to.

Bytecode — an interactive monograph on the CPython interpreter. Built with vanilla HTML, CSS and JavaScript; no frameworks, no build step. Keyboard-operable and built to WCAG 2.2 AA. The text-heavy listing and value-stack figures are real DOM, with `aria-current` on the active line; the object-graph and adaptive-interpreter figures use canvas with off-canvas radiogroup selection.
